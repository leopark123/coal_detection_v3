## 二、已知限制（接受风险，后续版本改进）

### 架构层面

| 编号 | 限制 | 影响 | 接受条件 | 建议改进时间 |
|------|------|------|----------|-------------|
| L1 | **采集窗口控制器是 per-funnel，但 PLC 标签是 per-machine** | 多漏斗共享同一套 PLC_CaptureCmd/CaptureState，当前通过"无相机不驱动"临时规避 | 当前单相机测试阶段无影响；多相机生产时**必须改** | 接入第 2 台相机前 |
| L2 | **配置变更非原子操作** | _save_config 失败时内存已变但 YAML 未保存，重启后丢失 | 错误提示明确（"内存已生效但未持久化"），运维人员可重试 | V3.1 |
| L3 | **运行时 add_machine 不区分 ImportError** | 如果运行时添加翻车机时依赖突然缺失（极不现实），PLC=None 但接口报成功 | 启动时已验证依赖存在，运行时不可能消失 | V3.1 |
| L4 | **启动中途失败时已创建资源未显式清理** | 如 pypylon 已装但 pycomm3 未装，先创建的相机不会被释放 | 进程退出时 OS 级回收；实际部署要么都装要么都没装 | V3.1 |

### 安全层面

| 编号 | 限制 | 影响 | 接受条件 |
|------|------|------|----------|
| L5 | 管理员 token 无过期机制 | SHA256(password) 固定不变，泄露后长期有效 | 工业内网，访问受限；上线前必须改默认密码 |
| L6 | WebSocket 视频流无鉴权 | 内网可看视频画面 | 工业内网，风险低 |
| L7 | 报警记录重启丢失（内存存储） | 无法追溯历史报警 | 日志文件可追溯；后续加 SQLite |

### 运维层面

| 编号 | 限制 | 影响 | 接受条件 |
|------|------|------|----------|
| L8 | logs/images/ 无自动清理 | 长期运行磁盘会满 | 手动清理或加 retention 策略 |
| L9 | PLC 连接被第三方挤掉后不自恢复 IPC_Online | 需重启恢复 | 正常运行不会出现；禁止用独立脚本直连 PLC |
| L10 | 单进程架构，崩溃有 5 秒空窗 | 看门狗 5 秒后自动重启 | PLC 梯形图 2 秒心跳超时保护 |

## 三、L1 架构改进方案（下一版本）

### 当前问题

```
machine-1 (PLC: 192.168.1.19)
├── funnel-1 → CaptureWindowController #1 → 读写 PLC_CaptureCmd/CaptureState
├── funnel-2 → CaptureWindowController #2 → 读写 同一组 PLC_CaptureCmd/CaptureState ← 冲突！
└── funnel-3 → CaptureWindowController #3 → 读写 同一组 PLC_CaptureCmd/CaptureState ← 冲突！
```

### 改进方案：采集控制器提升到 MachineState 级

```
machine-1 (PLC: 192.168.1.19)
├── MachineCapture Controller → 读写 PLC_CaptureCmd/CaptureState（唯一）
│   ├── 触发采集 → 通知所有漏斗的 worker 开始抓帧
│   ├── 停止采集 → 通知所有 worker 停止，汇总所有漏斗结果
│   └── 写 PLC 结果 → 综合所有漏斗的检测结果
├── funnel-1 worker → 只负责 grab + detect（不操作 PLC 标签）
├── funnel-2 worker → 只负责 grab + detect
└── funnel-3 worker → 只负责 grab + detect
```

### 改进要点

1. `CaptureWindowController` 从 `FunnelState` 移到 `MachineState`
2. 后台 worker 不再调 `tick()`，改为等待 machine 级事件通知
3. 窗口判定时汇总所有漏斗的结果（任一漏斗报警 → 整机报警）
4. PLC 标签读写只由 machine 级控制器执行

### 预计工作量

约 2-3 天。需要在接入第 2 台相机前完成。
